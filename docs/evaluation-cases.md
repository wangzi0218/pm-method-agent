# 典型体验用例

这篇不是标准答案集，而是一组用来体验和回归的真实感场景。

如果你不知道该输入什么，可以从这里挑一条跑。跑完后不要只看输出是否完整，更要看系统是否真的帮助你判断下一步。

## 怎么使用这些用例

推荐每个用例都按三步看：

1. 先输入原始草稿。
2. 看系统是否追问了关键缺口。
3. 补一轮信息，看它是否承接上一轮。

建议使用统一 agent 入口：

```bash
PYTHONPATH=src python3 -m pm_method_agent.cli agent \
  --workspace-id case-demo \
  "这里替换成用例输入"
```

## 用例 1：一线漏执行

输入：

```text
最近诊所前台经常漏掉复诊患者的就诊前提醒，店长担心会影响到诊率，我在想这件事是不是该处理。
```

期望观察：

- 系统应先补产品类型、平台和责任角色
- 不应直接建议做提醒弹窗
- 应提醒流程、管理或培训也可能先解决一部分

适合验证：ToB、流程型问题、一线角色、非产品路径。

## 用例 2：方案先行

输入：

```text
想增加一个新手引导浮层，提升新用户发帖率。
```

期望观察：

- 系统应识别“浮层”已经是方案
- 应追问新用户为什么不发帖
- 应要求补当前基线、目标用户和成功指标

适合验证：ToC、增长指标、方案先行、移动端打扰成本。

## 用例 3：指标异常但原因不明

输入：

```text
最近内容社区的新用户 7 日留存下降了，运营怀疑是首页内容不够吸引人，但我还不确定。
```

期望观察：

- 系统应区分现象和解释
- 应追问下降范围、用户分层和时间窗口
- 不应直接进入首页改版方案

适合验证：指标异常、归因不确定、增长场景。

## 用例 4：角色关系复杂

输入：

```text
门店员工反馈核销流程太麻烦，但总部运营更关心核销准确率，店长担心改简单后会增加误操作。
```

期望观察：

- 系统应识别多个角色目标不一致
- 应要求区分提出者、使用者和结果责任人
- 应提醒效率和准确率可能存在冲突

适合验证：ToB、多角色、目标冲突、权限与责任。

## 用例 5：看起来不急

输入：

```text
有几个客户提到希望预约记录能自动同步到日历，但现在反馈不多，研发资源也比较紧张。
```

期望观察：

- 系统应进入决策挑战，而不是默认产品化
- 应追问为什么现在做、延后损失是什么
- 应允许暂缓或先评估低成本替代方案

适合验证：优先级判断、机会成本、暂缓语义。

## 用例 6：移动端空间受限

输入：

```text
想在小程序订单页加一个售后提醒入口，减少用户找不到售后入口的问题。
```

期望观察：

- 系统应提醒小程序页面空间和打扰成本
- 应追问用户在哪一步找不到售后入口
- 应比较入口、搜索、订单状态提示等不同路径

适合验证：小程序、入口设计、空间约束。

## 用例 7：非产品路径可能更优

输入：

```text
客服说用户经常问会员权益怎么用，想在会员中心加一堆说明和提醒。
```

期望观察：

- 系统应追问用户到底在哪个触点不理解
- 应比较客服话术、运营触达、权益页结构和产品提醒
- 不应默认“加说明”就是最优解

适合验证：产品与运营边界、用户认知、非产品方案。

## 用例 8：用户只回答一半

第一轮输入：

```text
最近前台漏提醒复诊患者，我在想是不是要做一个提醒能力。
```

第二轮补充：

```text
这是 ToB 医疗场景，主要是前台使用。
```

期望观察：

- 系统应承接已回答部分
- 不应把未回答问题全部重复一遍
- 应只追最影响推进的缺口，比如结果责任人、频率、当前流程

适合验证：半步回答、多轮承接、追问克制。

## 怎么判断一次改动有没有退步

改动代码或文案后，可以抽 3 到 5 个用例重跑，看有没有出现这些问题：

- 每轮都像重新开始
- 用户已经回答了，系统还重复问
- 明明该停下来做决策，却继续往方案走
- 明明只是草稿，却输出很重的报告
- 角色识别明显离谱
- 方案挑战变弱，默认顺着用户方案走

如果出现这些问题，应优先修交互和阶段推进，而不是继续增加新分析模块。
