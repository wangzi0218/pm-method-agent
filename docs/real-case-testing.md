# 真实问题试跑

这篇写给想用自己真实需求试一轮的人。

不要为了测试系统而写“标准需求”。真实使用时，产品经理往往只有一个抱怨、一个指标异常、一个客户反馈，或者一个还没想清楚的方案念头。`PM Method Agent` 要优先接住这种输入。

## 你可以直接输入什么

可以直接输入这些不完整的内容：

- “最近前台总是漏提醒复诊患者，我在想是不是该处理。”
- “新用户注册后发帖率不高，运营想做新手引导，但我不确定问题是不是这个。”
- “售后投诉最近变多了，可能和退货流程有关，但我还没拆清楚。”
- “想加一个权益提醒浮层，提升会员权益感知。”

不需要一开始就补齐背景、角色、指标和方案。

## 一轮真实试跑怎么做

### 第一步：先给一句原始草稿

```bash
PYTHONPATH=src python3 -m pm_method_agent.cli agent \
  --workspace-id real-test \
  "最近诊所前台经常漏掉复诊患者的就诊前提醒，店长担心会影响到诊率，我在想这件事是不是该处理。"
```

先看它会不会问最关键的场景信息，而不是直接写方案。

### 第二步：按真实情况补一轮

```bash
PYTHONPATH=src python3 -m pm_method_agent.cli agent \
  --workspace-id real-test \
  "这是一个 ToB 的 HIS 产品，主要通过网页端使用，前台提出需求，店长和核心医生会对结果负责。"
```

这一步看它能不能承接上一轮，而不是重新开一个新问题。

### 第三步：补你的真实判断

```bash
PYTHONPATH=src python3 -m pm_method_agent.cli agent \
  --workspace-id real-test \
  "我暂时不确定是否值得投入研发，这个问题有客户反馈，但不像强痛点，可能更像 nice to have。"
```

这一步看它会不会把你的倾向承接成决策关口，而不是继续机械追问。

## 怎么判断效果好不好

一轮试跑后，可以按这几个问题打分：

- 它有没有先收住问题，而不是顺着方案展开
- 它有没有问到真正影响判断的信息
- 它有没有把角色、责任和目标差异说清楚
- 它有没有提醒非产品路径
- 它有没有在该停的时候停下来让你选择
- 你继续补充后，它有没有自然承接
- 输出读起来像协作中的产品同事，还是像模板机器人

如果至少 5 项成立，这个场景基本站得住。

## 推荐覆盖的场景

真实试跑不要只用一种需求。建议至少覆盖：

- 一线漏执行：例如前台、客服、门店店员漏操作
- 指标异常：例如转化率、留存、发帖率、到诊率下降
- 方案先行：用户一上来就说要弹窗、浮层、提醒、入口
- 角色复杂：提出者、使用者、付费者、责任人不一致
- 非产品可能更优：流程、培训、管理、运营可能先解决一部分
- 移动端空间受限：小程序、移动网页、原生应用上的打断成本更高

## 不同产品要看不同问题

ToB 产品更要看：

- 采购方、使用方、管理方是不是同一批人
- 问题是否发生在组织流程里
- 权限、责任和培训是否比功能更关键
- 做产品是否真的比流程治理更有效

ToC 产品更要看：

- 影响的是哪类用户
- 是真实动机问题，还是路径、认知、内容、信任问题
- 指标变化是否有明确基线和时间窗口
- 新功能会不会增加打扰或复杂度

PC 端更要看信息密度和效率。

移动端、小程序和移动网页更要看展示空间、打断成本和触达时机。

## 建议记录什么

每次真实试跑后，建议记录：

- 输入原文
- 系统追问了什么
- 哪个判断有帮助
- 哪个判断不自然
- 是否过问或漏问
- 你是否愿意继续用它分析这个需求

这些记录比“标准答案”更重要，因为这个项目要优化的是实际协作体验。
