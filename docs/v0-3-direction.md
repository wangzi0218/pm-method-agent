# v0.3 方向设计

> 文档状态：方向设计。用于启动 `v0.3` 前的取舍讨论，不等同于最终版本承诺。

`v0.2.0` 已经证明了最小的多轮协作、记忆闭环和网页演示。`v0.3` 不应该继续把所有能力都堆进网页，也不应该直接进入复杂 sub-agent 编排。

这一阶段更值得回答的问题是：

`PM Method Agent 应该怎样进入用户真实工作流？`

## 结论先说

`v0.3` 建议优先做：

1. 先定义并落地最小 IDE / Skill 入口。
2. 同步收敛 MCP 外壳边界，但不急着做完整 MCP 服务。
3. 网页演示继续作为本地体验入口，不升级成完整后台。
4. sub-agent 编排暂不进入主线，只保留设计观察。

一句话：

`先让它能被用户在真实写需求、写草稿、整理 issue 的地方自然触发。`

## 为什么不先继续做网页

网页最容易被用户体验到，但它也最容易把项目带向另一个方向：做一个完整 SaaS 后台。

这对当前阶段不是最优先，因为：

- `v0.2` 的网页演示已经能证明本地体验入口。
- 继续做网页很容易消耗大量精力在登录、列表、布局、权限和部署上。
- 这些工作不一定能增强 agent 内核。
- 产品经理真实产生草稿的位置，往往不是一个独立网页，而是文档、IDE、issue、聊天窗口或 agent 工作区。

所以 `v0.3` 可以继续小幅打磨网页，但不把“完整网页产品化”作为主目标。

## 为什么不先做 sub-agent

sub-agent 编排很有吸引力，但现在还早。

原因是：

- `v0.2` 刚刚证明主 agent 能承接 2 到 4 轮对话。
- 现在的问题更多是入口、触发、上下文复用和外壳契约，而不是计算并行不足。
- 如果过早引入 research / verification / synthesis 等角色，系统复杂度会明显上升。
- 用户短期更需要“我在哪里能用它”，而不是“内部有多少个代理”。

因此，sub-agent 更适合放到 `v0.4+`，等入口稳定后再设计。

## 为什么要看 IDE / Skill 入口

IDE / Skill 入口更接近这个产品的自然形态。

这里的 IDE 不只指代码 IDE，也可以理解为用户正在工作的宿主环境：

- 写需求文档的地方
- 管理 issue 的地方
- 和 AI agent 协作的地方
- 整理产品草稿的地方
- 内部知识库或项目工作区

用户不应该为了问一句“这个需求值不值得做”，先打开一个复杂后台。更自然的方式是：

1. 用户在当前上下文里输入一句草稿。
2. Skill 把原话交给 PM Method Agent。
3. Agent 返回当前判断、卡点和下一步。
4. 用户继续自然补充。
5. 项目背景和偏好在用户确认后复用。

这和 `v0.2` 已经做好的工作区、案例承接、记忆建议正好匹配。

## Skill 入口的最小契约

`v0.3` 第一版 skill 不需要自己变聪明。

它只需要稳定做好 5 件事。

### 1. 触发

支持用户用自然语言触发，例如：

- “帮我看看这个需求值不值得做。”
- “这个点子我还没想清楚，帮我拆一下。”
- “基于当前文档，看看下一步该补什么。”
- “这是不是已经可以进入方案设计？”

第一版不需要复杂按钮和表单。

### 2. 输入

最小输入就是一段文本。

可选增强输入包括：

- 当前文件或选中文本
- 当前 issue / ticket 标题和描述
- 当前项目背景
- 用户偏好

但这些都应该被整理成一条消息，交给统一入口：

```text
POST /workspaces/{workspace_id}/messages
```

### 3. 输出

第一版优先展示：

- `message`
- `rendered_card`
- 当前 `case_id`
- 当前 `stage`
- 当前是否 `blocked / deferred / done`

不要一开始就强行拆成复杂 UI 区块。

### 4. 承接

skill 必须保留工作区概念。

至少要做到：

- 同一个项目或目录下复用同一个 `workspace_id`。
- 用户继续补充时，默认承接当前活跃案例。
- 用户明确说“另一个问题”时，创建新案例。
- 用户说“不是这个项目”时，不要强行复用旧背景。

### 5. 记忆

第一版只展示记忆建议，不静默写入长期记忆。

最低要求：

- 用户能看到系统想记什么。
- 用户能确认或忽略。
- 被采用的项目背景要在输出里可见。
- 新输入和旧背景冲突时，新输入优先。

## MCP 的位置

MCP 更像是面向其他 agent 的工具协议，不是普通用户的第一入口。

`v0.3` 可以先做 MCP 设计收敛，但不建议马上把它作为主要交付。

原因是：

- MCP 的价值主要体现在“被其他 agent 调用”。
- 普通产品经理很难直接感知 MCP 本身。
- 当前 HTTP 服务已经能作为最小中间层。
- 如果 Skill 入口先跑通，MCP 可以复用同一套消息契约。

所以 MCP 在 `v0.3` 的定位是：

- 先定义工具边界。
- 先明确哪些能力适合暴露为工具。
- 不急着做完整协议适配。

## v0.3 第一批任务建议

### P0：方向和契约

- 补全 Skill 入口最小契约。
- 明确 workspace_id 如何从项目、目录或宿主环境派生。
- 明确 skill 输出应该优先展示哪些字段。
- 明确“继续当前案例 / 新建案例 / 套用项目背景 / 否定项目背景”的行为。

### P1：最小 Skill 包装

- 提供一个可复制的 skill 描述草稿。
- 提供一组命令示例，能调用本地 HTTP 服务或 CLI。
- 输出保持轻量，不做复杂 UI。
- 保留用户确认记忆写入的边界。

### P2：MCP 设计收敛

- 列出候选 MCP tools。
- 区分只读工具和写入工具。
- 明确哪些动作必须审批。
- 明确 MCP 先不替代 HTTP 服务。

### P3：网页小幅同步

- 如果 skill 入口暴露出新的理解问题，再反向同步到网页 demo。
- 不把网页升级成账号系统或团队后台。

## v0.3 暂不做

- 不做完整云端多用户平台。
- 不做正式 SaaS 后台。
- 不做复杂 sub-agent 编排。
- 不做完整 PRD 自动生成。
- 不把所有上下文都静默写入长期记忆。
- 不让外壳自己重写主 agent 的阶段推进逻辑。

## 判断 v0.3 是否成功

如果 `v0.3` 做得对，应该能看到这些结果：

- 用户可以在一个外部工作环境里触发 PM Method Agent。
- 用户不需要重新解释每个项目背景。
- skill 能复用 `v0.2` 的工作区、案例、记忆和渲染结果。
- 用户能看懂当前卡点和下一步。
- 外壳很薄，核心判断仍然在 PM Method Agent 内核里。

如果最后变成：

- 一个越来越重的网页后台；
- 一个只会转发 prompt 的 skill；
- 一个过早复杂化的多 agent 系统；

那就说明 `v0.3` 方向跑偏了。
