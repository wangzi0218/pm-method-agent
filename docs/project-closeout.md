# 项目收尾说明

> 文档状态：收尾文档。用于说明 `PM Method Agent` 当前适合停在哪里，以及后续如何作为新项目的参考资产。

## 当前结论

`PM Method Agent` 不建议继续追求“完全体”。

它现在更适合被固定为：

`一个本地可运行的产品判断 agent 内核预览版，以及后续产品化项目的参考实现。`

当前已经发布：

- `v0.1.0`
- `v0.2.0`

其中 `v0.2.0` 已经证明：

- 模糊产品草稿可以被接住。
- 多轮补充可以被承接。
- 方法阶段和决策关口可以被运行时控制。
- 项目背景和记忆建议可以被用户看见、确认和复用。
- CLI、HTTP 服务、网页 demo 可以共用同一套方法内核。

## 为什么现在适合收尾

继续在这个仓库里追完整产品，会遇到几个问题：

- 这个项目已经承载了大量方法、运行时、工具、安全、网页和文档设计。
- 它适合作为“探索样板”，但不适合继续无边界扩张。
- 如果继续做完整网页、MCP、IDE 插件、sub-agent 和团队协作，会把项目变成一个复杂平台。
- 你下一步真正想做的是一个更清晰、更高效、面向产品经理团队或个人提效的新产品。

所以更稳的策略是：

1. 保留这个项目作为方法内核和架构参考。
2. 把 `v0.3` 文档视为后续入口方向参考，而不是当前必须完成的承诺。
3. 新开一个更小范围的新项目，重新定义用户、场景、入口和交付边界。

## 当前项目已经值得保留的资产

### 1. 方法资产

- 问题定义
- 决策挑战
- 验证设计
- 阶段关口
- 暂缓、阻塞、继续、完成等终止语义
- 对“方案先行”的方法拦截

### 2. Agent 运行时资产

- workspace / case / runtime session
- query loop
- event log
- execution ledger
- pending approvals
- context budget
- memory suggestion

### 3. 交互资产

- 多轮自然语言承接
- 半步回答处理
- 项目背景复用
- 新背景覆盖旧背景
- 网页 demo 的轻量阅读结构

### 4. 工程资产

- CLI 入口
- 本地 HTTP 服务
- OpenAI-compatible LLM adapter
- 本地规则回退
- 自动化回归样本
- 发布准备清单

这些资产后续可以被新项目选择性吸收，但不应该全部搬过去。

## 当前项目不再继续追的方向

为了避免范围继续膨胀，建议当前仓库暂不继续推进：

- 完整 SaaS 网页后台
- 云端多用户系统
- 正式 IDE 插件
- 正式 MCP server
- sub-agent 编排
- 完整 PRD 自动生成
- 复杂团队权限与组织管理

这些方向不是没有价值，而是更适合在新项目里重新按产品目标选择。

## 收尾后仍可维护什么

当前项目后续只建议做三类维护：

1. 修明显 bug。
2. 补必要文档说明。
3. 把新项目中验证有效的核心抽象，反向沉淀为参考文档。

不建议继续把每个新想法都塞回这个仓库。

## 给新项目的迁移建议

新项目不要从“把 PM Method Agent 做完整”开始。

更适合从下面的问题开始：

- 产品经理每天最频繁、最耗精力的 1 到 2 个场景是什么？
- 这些场景更像个人提效，还是团队协作？
- 用户会在哪里触发：文档、聊天、issue、浏览器、IDE、还是独立网页？
- 系统要记住什么，什么必须由用户确认？
- 哪些事情必须由 runtime 控制，不能交给一段 prompt？

新项目可以复用这里的架构经验，但要重新收窄产品面。
